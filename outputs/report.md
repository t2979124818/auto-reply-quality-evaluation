# 自动回复质量评估报告

- 数据集：20 条自动回复（在线客服场景）
- 判官：`mock-rules-v1`
- 总分口径：0-100（加权和 × 100，再套用闸门降级）；等级阈值 ≥85 良好 / 70~84.9 需改进 / 0~69.9 不合格

## 一、结论

**整体水位 73.1 / 100（中位数 74.9，区间 60.2 ~ 86.5）**；等级分布：良好 1 条 / 需改进 11 条 / 不合格 8 条。

三条与业务直觉相关的发现：

1. **主要问题不是「说错了」，而是「说对了但没办事」。** 事实准确性均值 0.98、无编造性均值 0.88，属于健康水位；但解决力均值只有 2.44/5，推进完备性 3.23/5。所以扩张覆盖范围前要改的是话术策略与数据接入，而不是再加一层事实校验。
2. **「不瞎编」在本数据集没有触发红线**：21 条断言被 KB 支持、1 条与 KB 冲突、2 条无法核实，闸门命中 0 条。这是好信号，但**不代表可以删掉这条指标**——编造风险会随覆盖类目（尤其是具体商品参数）扩大而暴露，当前处于「没被检验」而非「已验证安全」。
   从抽取量也能看出这个天花板：平均每条回复只能判定 **1.2** 条事实断言（抽取到的断言里占 36%）；且其中 **8 条**回复没有任何可核实断言，它们的 accuracy = 1.00 属于「空真」（没说什么 ≠ 说对了），所以准确率均值 0.98 要打折看。
3. **最差 3 条**：case_01、case_06、case_13。共同特征是「把动作推回给用户」——让用户自己去翻详情页、自己联系快递、自己再问一遍。

## 二、评估口径：模糊词 → 可计算指标

| 业务原话 | 指标 | 权重 | 量化方式 | 为什么这样定义 |
| --- | --- | --- | --- | --- |
| 准确 | **事实准确性**<br>`accuracy` | 0.2 | 把回复拆成原子断言（claim）→ 与知识库比对 → 三分类：supported（与 KB 一致）/ contradicted（与 KB 冲突）/ unverifiable（KB 无法判定）。accuracy = supported / (supported + contradicted)，unverifiable 不计入分母（它们计入 M2，避免'不知道'被算成'说错'）。 | 业务方说'要准确'，本质是'用户不能按错误信息行动'。所以必须做 claim 级别的比对，而不是让模型整体打个'准不准'的分——后者无法定位到底哪句话错了，也无法回归测试。 |
| 不能瞎编 | **无编造性（幻觉率反面）**<br>`groundedness` | 0.25 | 对每条可判定断言按类型给「可信分」：supported=1.0，contradicted=0，unverifiable 按风险分档（政策数值 / 商品参数 / 金额承诺 0.4~0.5，系统能力断言 0.85），再用 0.85 的先验做小样本平滑。另有一条硬规定：若整条回复没有任何被支持的断言、却至少有一条「高风险且无法核实」的断言，则无编造性直接封顶 0.50（防止一句编造的时效数值靠平滑拿到高分）。重点监控三类高风险断言：具体商品参数、具体金额补偿承诺、政策数值。 | '不瞎编'和'准确'不是一回事：准确是'说的都对'，不瞎编是'不知道就别装知道'。自动回复的最大合规风险不是反驳用户，而是**编造一个具体数字/具体参数**——所以 unverifiable 必须被单独惩罚，而不能当成'没答错'放过。 |
| 有用 | **解决力（主动服务程度）**<br>`resolution` | 0.25 | 1-5 分锚点式 rubric（见 RUBRIC_RESOLUTION），由 LLM/规则判官按显式信号打分：基线 3 分，主动承接 +1.0、追问必要信息 +0.5、给出明确结论 +0.5、感谢并承接反馈 +0.8；推诿每处 -0.6（最多 -1.5）、把内部事项当答复 -0.5、答非所问 -1.0、先排查后给方案 -0.5；若首句就是推诿，则该条最多 3.0 分（后面的条件承诺无法赎回主干动作）。 | 本数据集最主流的失败模式是'正确但没用'：回复内容没错，但用户还得自己去翻页面、自己联系快递、自己再问一遍。业务方要'有用'，翻译成可测的话就是'用户看完这条回复，下一步动作的负担有没有降低'。 |
| 有用 | **推进完备性**<br>`completeness` | 0.15 | 按 case 意图判断：transactional（必须补信息）/instance（问的是'这个/我的'具体对象）/ policy（通用规则）。transactional 且既没追问也没承诺代办 → 1.5 分；instance 且没给出该对象的实际信息 → 2 分；通用政策题给出完整规则+结论 → 4.5 分。 | 把'有用'拆成两半，是因为两者的修复手段完全不同：solution 类问题要靠改写话术（改成'我帮您查'），completeness 类问题要靠接数据（商品库/订单系统）。混在一起打分，就看不出该改 prompt 还是该加接口。 |
| 语气好 | **语气与共情**<br>`tone` | 0.15 | 1-5 分锚点式 rubric（见 RUBRIC_TONE）。规则判官检测：道歉/共情词、用户是否带情绪（需要安抚）、是否出现指责性表达、是否过度承诺（'保证/一定/100%'）、是否把内部事项当主回复。 | '语气好'是主观词，但可操作的定义是：**在用户已经带情绪的 case 上有没有安抚**。中性问题（问材质、问政策）不需要煽情，所以指标按'是否需要安抚'条件化，避免把所有回复都往'多道歉'的方向带偏。 |

### 打分锚点（写死在代码里，可人工复核）

**解决力 `resolution`**

| 分 | 锚点 |
| --- | --- |
| 5 | 直接给出可执行解法，并主动承接后续动作（'我帮您查/我帮您操作'） |
| 4 | 给出明确解法与操作路径，用户可以自己完成，且路径具体到可点击/可执行 |

| 分 | 锚点 |

| 4 | 有礼貌且表达歉意/理解，措辞得体 |
| 3 | 中性、公事公办；情绪场景下缺少安抚 |

### 优先级（对应问题 5）

| 优先级 | 理由 |
| --- | --- |
| P0 · 无编造性 | 合规/安全红线。编造一个政策数字或商品参数，用户会照做并产生实际损失，且是平台担责。用**闸门**而非加权，是因为 0.25 的权重不足以否决一条'语气完美但编了数据'的回复。 |
| P1 · 事实准确性 | 同样是'用户会照做'的风险，但比编造低一档（说错的是已有信息，可归因、可纠正）。同样用闸门（<0.60 封顶 70 分）。 |
| P2 · 解决力 | 决定用户是否真的省事，是业务方最关心的'有没有用'。但它不会造成损失，只造成体验差，所以放在两个风险闸门之后。 |
| P3 · 推进完备性 | 同样影响'有用'，但更多受系统能力限制（能不能查订单），优先级低于话术层面就能改善的解决力。 |
| P4 · 语气与共情 | 影响满意度和一次解决率，但在'答对'和'能办'之后。语气好但答错，业务价值为负。 |

> 关键机制：P0/P1 不参与加权，而是作为**闸门**（不达标就封顶总分）。纯加权求和会让「语气满分」稀释掉「编造了政策数值」，而这两件事的业务成本差一个量级。

## 四、最差 3 条 case 分析

### 1. `case_01`（快递放错柜取不出）· 总分 60.2 / 不合格

- **用户问题**：我的快递到了但是放错快递柜了，取不出来
- **自动回复**：您好，如果快递放错了快递柜，您可以尝试联系快递员重新派送，或者到放错的快递柜去取。建议您先查看取件码确认具体位置。如果无法解决，请联系我们的客服，我们会协助您处理。
- **人工参考回复**：这种情况我帮您联系快递公司重新派送到您附近的快递柜或者送货上门，预计需要1-2天。请您提供一下订单号，我来帮您处理。
- **各指标**：准确 1.0 / 无编造 0.85 / 解决力 1.5 / 完备性 1.5 / 语气 2.3
- **扣分信号**：推诿 ['让用户自己再联系一次客服', '让用户自己联系快递方', '让用户自行处理']；主动承接=无；追问必要信息=无；答非所问=否
- **人工标注裁定**：`weak` —— 把责任推给了用户，没有体现主动服务意识
- **事实性问题断言**：无。事实层面站得住，低分完全来自「不好用」。

## 六、正文之外的数据发现

1. **质保天数自相矛盾**：`case_04` 说「7 天质保期」，`case_18` 说「30 天质保期」，两条都被人工作为「基本正确」接受。这说明平台缺少统一的政策事实源——这类「看起来都对」的不一致，恰恰是线上投诉和资损的高发点，而单条评估永远发现不了。
2. **发现 1 条真实的事实错误**：`case_11` 无条件声明「换货运费由买家承担」，与 `case_09` 体现的政策（质量问题由商家承担）冲突。这是本数据集里唯一被判为 contradicted 的断言。
3. **模板化推诿**：多条回复以「建议您查看…／请联系客服…」收尾，把用户重新推回自助流程，是解决力低分的直接来源，也是最容易用 prompt 改掉的部分。

> 这三条差异不是调参失误，而是两种尺子的系统性错位：人工参考回复包含「查订单、代操作」这类**自动回复结构上没有的能力**。把这类动作计入扣分，就相当于罚一辆自行车“不会飞”。真实结论应该是：**当前自动回复的能力上限，决定了它在“需要查数据”的意图上天花板就这么高**，要突破得接系统，而不是改文案。

## 七、局限性（哪些 case 可能评不准）

1. **基准循环（最根本的一条）**：事实类指标的基准 KB 是从人工参考答案反推的，而一致性回测的黄金标签也来自同一份文件。这属于「用同一份数据既当老师又当考卷」：只能证明「自动评分与这位标注者同向」，不能证明「自动评分是对的」。改进：另找 1-2 名标注者盲标 50-100 条，只用双方一致的部分做金标准。
2. **能力边界错配（最影响结论的一条）**：人工参考答案的隐含标准是「人工客服可以查订单、可以代操作」。自动回复没有这些权限，所以在「解决力 / 推进完备性」上会被系统性低估——这类扣分不该归因于「回复写得不好」，而该归因于「产品没接数据」。改进：声明一层能力边界（当前自动回复可做/不可做的动作清单），不可做的动作不计入解决力扣分，并单独统计「能力缺口导致的低分」占比。
3. **政策数值缺乏权威来源**：KB 同时接受 7 天和 30 天质保，退款时效也只做了「数值是否落在允许集合内」的弱判断。因此当同一政策在不同回复中取值不同时，本方法判不出来（case_04 vs case_18 就是实例）。改进：把政策库升级为受版本管理的线上事实源，校验「回复数值 == 政策源当前值」，并记录政策变更时间点，避免用新政策去评旧回复。
4. **「无编造」指标存在天花板效应**：本数据集里没有出现真实编造（正面的解释是回复很保守，负面的解释是这条指标没被真正检验）。一旦开放具体商品类目（参数、库存、成分），幻觉才会真实暴露。改进：用对抗集压测——人工构造含错误参数/过期政策的回复，验证闸门能否拦下。
5. **规则判官对改写敏感**：推诿 / 承接 / 追问靠正则召回，同义改写（「帮您看看」vs「咱们处理一下」）会漏判；长句更容易命中多个推诿模式，存在累加偏差。改进：一是把规则判官降级为回归基线，用 LLM 判官做主力（已实现 --mode llm，共用同一 rubric 与输出结构，可算两者一致性）；二是抽 200 条线上样本，单独统计这些规则的精确率/召回率，而不是只看总分。
6. **单轮视角，看不到会话级问题**：评估只看「这一句提问 + 这一条回复」。多轮追问、重复回复、前后轮信息不一致（这轮要订单号、下轮又变了）都测不到。改进：补会话级检查项——关键信息索取的幂等性、已答过的问题不重复问。
7. **部分场景的判准本身有争议**：case_08（手机壳材质）人工判「正确但没用」，但自动回复确实给出了 TPU 软胶这一正确参数，只是结尾又加了「可以查看详情页」。claim 级判官会记为「准确且针对性强」，与人工的整体判断产生 2 档分歧（本数据集最大分歧之一）。改进：对这类「答了但仍让用户多走一步」的回复单列「尾部推诿」信号，而不是靠一个整体分把它掩盖掉。

| 优先级 | 动作 | 依据 |
| --- | --- | --- |
| P0 | 接入真实政策事实库（退款时效 / 质保 / 运费归属），让事实类指标脱离人工参考答案独立运行 | 本次发现质保天数自相矛盾（7 天 vs 30 天），当前 KB 判不了 |
