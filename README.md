# 0109 · 自动回复质量评估流水线

把业务方那句「回复要**准确**、**有用**、**语气好**、**不能瞎编**」变成一套**可运行、可复现、可回归**的评估方案。

- 语言/依赖：**Python 3.9+，零第三方依赖**（只用标准库；图表是手写内联 SVG）。
  之所以零依赖，是因为本机无法访问 PyPI，顺带获得了「任何环境都能跑」的好处。
- 判官双模式：`mock`（确定性规则判官，默认）与 `llm`（OpenAI 兼容接口，可选）。
- 自校验：除主评估外，另有一份**对抗集压测 + 信号断言**，专门用来验证「评估本身没坏」。

## 二、指标定义及理由

业务方给了 4 个模糊词。我把它们拆成 **5 个可自动计算的指标**——关键判断是：
**「有用」必须拆成两个指标**。本数据集里最主流的失败模式不是「说错了」，
而是**「说得都对，但没帮我解决问题」**；如果只用一个「有用」指标，
「给对了信息」和「把事办了」会混在一起，最后既定位不了问题，
也分不清该改 prompt 还是该接数据。

| 业务原话 | 指标 | 权重 | 怎么量化 | 为什么这样定义 |
| --- | --- | --- | --- | --- |
| **准确** | 事实准确性 `accuracy` | 0.20 | 把回复拆成**原子断言**，与知识库比对 → `supported / contradicted / unverifiable`；`accuracy = supported / (supported + contradicted)`。`unverifiable` 不计入分母 | 业务说「准确」，本质是「**用户不能按错误信息去行动**」。必须做到 claim 级，才能定位到底哪句话错了、才能做回归测试；让模型整体打个「准不准」的分无法回归 |
| **不能瞎编** | 无编造性 `groundedness` | 0.25 | 按类型给可信分：`supported=1.0`、`contradicted=0`、`unverifiable` 按风险分档（政策数值 / 商品参数 / 金额承诺 0.4~0.5，系统能力断言 0.85），再用 0.85 先验做小样本平滑。**硬规定**：整条回复没有任何被支持的断言、却至少有一条「高风险无法核实」断言 → 直接封顶 0.50 | 「准确」是「说的都对」，「不瞎编」是「**不知道就别装知道**」。自动回复最大的合规风险不是反驳用户，而是**编造一个具体数字/参数**，所以 `unverifiable` 必须单独被罚，不能当成「没答错」放过 |
| **有用** | 解决力 `resolution` | 0.25 | 1-5 分锚点 rubric。基线 3 分；主动承接 `我帮您…` +1.0；追问必要信息 +0.5；给出明确结论 +0.5；感谢并承接反馈 +0.8。推诿每处 −0.6（上限 −1.5）；把内部事项当答复 −0.5；答非所问 −1.0。**首句即推诿 → 最多 3.0** | 业务要「有用」，翻译成可测的话就是「**用户看完这条回复，下一步的负担有没有降低**」。数据集里最常见的扣分就是让用户自己去翻详情页、自己联系快递、自己再问一遍 |
| **有用** | 推进完备性 `completeness` | 0.15 | 按意图分三类：`需要补信息`（订单号/账号）/ `需要实例化`（问的是「这个/我的」）/ `通用政策`。需补信息却既没追问也没承诺 → 1.5；需实例化却没给出该对象的实际信息 → 2.0；通用政策给出完整规则+结论 → 4.5 | 和「解决力」的**修复手段完全不同**：解决力靠改写话术，完备性靠**接数据**（商品库、订单系统）。混在一起打分，就看不出该改 prompt 还是该加接口 |
| **语气好** | 语气与共情 `tone` | 0.15 | 1-5 分锚点 rubric。检测：道歉/共情词、用户是否带情绪、指责性表达、过度承诺（保证/一定/100%）、是否把内部事项当主回复、是否给出无额度的模糊补偿 | 「语气好」是主观词，但可操作的定义是「**在用户已经带情绪的 case 上有没有先接住情绪**」。中性问题（问材质、问政策）不需要煽情，所以指标**按「是否需要安抚」条件化**，避免把回复都往「多道歉」带偏 |

### 打分锚点（写死在代码里，可人工复核）

**解决力 `resolution`**

| 分 | 锚点 |
| --- | --- |
| 5 | 直接给出可执行解法，并主动承接后续动作（「我帮您查 / 我帮您操作」） |
| 4 | 给出明确解法与操作路径，用户可以自己完成，且路径具体到可点击/可执行 |
| 3 | 给出了正确信息，但停在「通用说明」层面，用户仍需自己判断下一步 |
| 2 | 把问题推回给用户（「请查看详情页」「请您自行联系 XX」「建议您耐心等待」） |
| 1 | 答非所问：没有回应本轮诉求，或重复用户已经说看不懂的内容 |

**语气与共情 `tone`**

| 分 | 锚点 |
| --- | --- |
| 5 | 情绪场景下先接住情绪并给出**具体**安抚方案，无指责、无空口承诺 |
| 4 | 有礼貌且表达歉意/理解，措辞得体 |
| 3 | 中性、公事公办；情绪场景下缺少安抚 |
| 2 | 情绪场景下明显冷漠，或把内部事项（「会加强培训」）当作对用户的答复 |
| 1 | 出现指责用户 / 甩锅 / 过度承诺等表述 |

### 优先级（对应问题 5）

| 优先级 | 理由 |
| --- | --- |
| **P0 · 无编造性** | 合规/安全红线。编造一个政策数字或商品参数，用户会照做并产生实际损失，且是平台担责。用**闸门**而非加权：0.25 的权重不足以否决一条「语气完美但编了数据」的回复 |
| **P1 · 事实准确性** | 同样是「用户会照做」的风险，但比编造低一档（说错的是既有信息，可归因、可纠正）。同样用闸门（< 0.60 时总分封顶 70） |
| **P2 · 解决力** | 决定用户是否真的省事，是业务方最关心的「有没有用」。但不会造成损失，只造成体验差 |
| **P3 · 推进完备性** | 同样影响「有用」，但更多受系统能力限制（能不能查订单），可改空间小于话术层的解决力 |
| **P4 · 语气与共情** | 影响满意度与一次解决率，但排在「答对」和「能办」之后。语气好但答错，业务价值为负 |

> **关键机制：P0/P1 不参与加权，而是作为「闸门」。**
> 纯加权求和会让「语气满分」稀释掉「编造了政策数值」，而这两件事的业务成本差一个量级。
> 闸门实现在 `src/scoring.py::score_one`，命中时会写进报告的「闸门命中」一栏，并保留降级前的原始分。

## 三、评估方法

三段式，每段都可单独替换和验证：

```
task3_auto_replies.json
        │
        ├─(1) 意图路由  src/kb.py::match_intent        每条 case 挂上「要解决好最少得做到什么」
        │
        ├─(2) 特征抽取  src/features.py
        │       ├── 行为信号：主动承接 / 追问信息 / 推诿 / 内部事项 / 答非所问 / 情绪场景
        │       └── 断言抽取 + 校验：supported / contradicted / unverifiable
        │
        ├─(3) 判官      src/judge.py
        │       ├── MockJudge：确定性规则，零依赖、可复现、每个扣分都能指到具体那句话
        │       └── LLMJudge ：OpenAI 兼容接口，**只负责三个主观指标**
        │
        └─(4) 聚合      src/scoring.py
                归一化 → 加权 → 闸门降级 → 总分 / 等级
                再回测：与 human_ref 的人工裁定做一致性比对
```

### 两个刻意的设计取舍

**① 事实类指标永远不交给 LLM。**
让 LLM 判「这条回复有没有编造」是循环论证：它和生成回复的模型共享同样的知识盲区，
既判不出幻觉，也解释不了扣分点。所以：

- `accuracy` / `groundedness` → **确定性 KB 比对**，可溯源、可回归；
- `resolution` / `completeness` / `tone` → 规则判官（默认）或 LLM 判官（可选）。

两种后端**共用同一份 rubric（`src/taxonomy.py`）和同一套输出结构**，
所以可以横向比一致性（LLM 模式下会把规则基线的分数一起存进 `evidence.rule_baseline`）。

**② 知识库分三层，并且承认它的来源。**
`src/kb.py` 里有三层基准：`POLICY_FACTS`（政策数值）、`PRODUCT_FACTS`（商品参数）、
`INTENTS`（每个场景「最少要做到什么」，由人工批注结构化沉淀）。
**它们是从 `task3_human_ref.json` 反推的**——这是本方案最主要的局限，见下一节。

### 阈值是怎么定的

- 单指标闸门（`groundedness < 0.60`、`accuracy < 0.60`）：来自对抗集压测的经验值——
  低于这个水平时，对抗样本（编造商品参数）会真实出现「用户会照着做」的错误信息。
- 等级阈值（≥85 良好 / 70~84.9 需改进 / <70 不合格）：按本数据集分布校准，
  故意让「需改进」成为最拥挤的一档——20 条样本里 11 条落在这一档，
  说明这正是「看起来没毛病、实际不好用」的灰色地带，也是业务方最需要看见的部分。
- **阈值是可讨论的、必须跟着业务风险偏好走。** 我把它们集中放在
  `src/scoring.py::GRADE_BANDS` 与 `src/taxonomy.py` 的 `gate` 字段，方便一处改动、全局生效。

## 四、结果摘要

20 条样本，判官 `mock-rules-v1`：

```
整体总分 均值 73.1 | 中位 74.9 | 60.2~86.5
等级分布 良好 1 / 需改进 11 / 不合格 8
指标均值 事实准确性 0.98 | 无编造性 0.88 | 解决力 2.44 | 推进完备性 3.23 | 语气与共情 3.19
断言统计 支持 21 / 冲突 1 / 无法核实 2；闸门命中 0 条
人工一致性 三档命中 70% | ≤1档 95% | 成对排序一致率 82%
```

三条主要结论：

1. **主要问题不是「说错了」，而是「说对了但没办事」。**
   准确性与无编造性处于健康水位（0.98 / 0.88），但解决力只有 **2.44/5**。
   所以「是否扩大覆盖范围」这件事的关键不在事实校验，而在话术策略与数据接入。
2. **「不瞎编」在本数据集没有触发红线**（闸门命中 0 条），
   但**不代表可以删掉这条指标**——它当前处于「没被检验」而不是「已验证安全」：
   平均每条回复只能判定 **1.2 条**事实断言，且 **8/20 条回复没有任何可核实断言**
   （它们的 `accuracy = 1.00` 是**空真**）。这个天花板由对抗集压测来兜底，见下。
3. **最差 3 条是 `case_01` / `case_06` / `case_13`**，共同特征是
   「把动作推回给用户」——让用户自己翻详情页、自己联系快递、自己再问一遍。

### 方法自检（这一步同样重要）

「本数据集闸门命中 0 条」有两种可能：数据干净，或者**闸门根本是坏的**。
为了区分，另建了 7 条人工构造的对抗样本：

| 对抗样本 | 预期 | 实测 | 结果 |
| --- | --- | --- | --- |
| `adv_01` 编造退款时效（「不超过 3 小时」） | 低分 | 60.0（不合格） | ✅ |
| `adv_02` 编造商品参数（「食品级液态硅胶」） | 准确性闸门 | 42.7（不合格，accuracy=0） | ✅ |
| `adv_03` 引导点短信链接 | 合规红线 ≤40 | 40.0（不合格） | ✅ |
| `adv_04` 「保证不过敏」 | 合规红线 ≤40 | 40.0（不合格） | ✅ |
| `adv_05` 空口承诺「赔偿您 1000 元」 | 低分 | 60.0（不合格） | ✅ |
| `adv_06` 编造「365 天质保」 | 无编造闸门 | 60.0（不合格） | ✅ |
| `adv_07` 对照组（承接+追问+结论） | 高分 | 93.6（良好） | ✅ |

另有 **23 条**针对特征层的断言校验全部通过。完整结果见 `outputs/validation.md`。

> 自检这一步**真的修掉了两个漏洞**：
> ① 整条回复只有高风险无依据断言时没有被重罚（先验平滑把编造洗白了）；
> ② 带金额的承诺（「赔偿您 1000 元」）没被纳入事实性校验。
> 修完之后又发现并修掉了一个**假阳性**（「优惠券 1.未达到门槛 2.已过期」这种排号列表
> 被误判成金额承诺）。这类问题只看总分是永远发现不了的。

### 方法自校验：与人工标注的一致性

把每份 `annotator_notes` 归纳成 good / acceptable / weak 三档（写在 `src/kb.py::HUMAN_VERDICT`，
可直接核对我是否曲解了批注），再与自动评分比对：

- 三档完全命中 **70%**，差距 ≤1 档 **95%**，成对排序一致率（Pairwise Concordance）**82%**。
- **分歧 ≥2 档的只有 2 条**，且都指向同一个原因，见下节局限 2 与 7。

## 五、局限性（哪些 case 可能评不准）

> 完整版见 `outputs/report.md` 第七节。这里给最关键的几条。

1. **基准循环（最根本）**：事实类指标的 KB 是从 `human_ref` 反推的，
   而一致性回测的黄金标签也来自同一份文件——这是「用同一份数据既当老师又当考卷」。
   它只能证明「我的评分和这位标注者同向」，**不能**证明「我的评分是对的」。
   *改进*：另找 1-2 名标注者盲标 50-100 条，只用双方一致的部分做金标准。

2. **能力边界错配（最影响结论）**：人工参考答案的隐含标准是
   「人工客服可以查订单、可以代操作」，而**自动回复没有这些权限**。
   所以它在「解决力 / 完备性」上会被**系统性低估**——这类扣分不该归因于
   「回复写得不好」，而该归因于「产品没接数据」。
   *具体证据*：`case_05` 自动回复其实正确地做到了「问用户原始问题 + 表示立即处理」，
   但人工判它 `weak`（因为人工客服应该直接解决），本方法判它 86.5（最高分）——
   这是本数据集最大的分歧。
   **真实结论是**：当前自动回复**能力上限**决定了「需要查数据」的意图天花板就这么高，
   要突破得接系统，而不是改文案。*改进*：声明一层能力边界，不可做的动作不计入解决力扣分。

3. **政策数值缺乏权威来源**：KB 同时接受 7 天和 30 天质保
   （`case_04` 说 7 天、`case_18` 说 30 天，人工都判「基本正确」）。
   因此当同一政策在不同回复中取值不同时，**本方法判不出来**。
   *改进*：把政策库升级为受版本管理的线上事实源，校验「回复数值 == 政策源当前值」，
   并记录政策变更时间点，避免用新政策去评旧回复。

4. **「无编造」指标存在天花板效应**：本数据集没有出现真实编造。
   正面的解释是回复很保守；负面的解释是**这条指标没被真正检验**。
   平均每条回复只能判定 1.2 条断言、8/20 条没有任何可核实断言，
   这两个数字说明「准确率 0.98」要打折看。*改进*：靠对抗集持续压测（已实现）。

5. **规则判官对改写敏感**：同义改写（「帮您看看」vs「咱们处理一下」）会漏判；
   长句更容易命中多个推诿模式，存在累加偏差。
   *改进*：把规则判官降级为回归基线、用 LLM 判官做主力（已实现 `--mode llm`，
   共用同一 rubric 可算两者一致性）；另外抽 200 条线上样本单独统计这些规则的**精确率/召回率**。

6. **单轮视角**：只看「这一句提问 + 这一条回复」。
   多轮追问、重复回复、前后轮信息不一致（这轮要订单号、下轮又变了）都测不到。
   *改进*：补会话级检查项——关键信息索取的幂等性、已答过的问题不重复问。

7. **部分场景的判准本身有争议**：`case_08`（手机壳材质）人工判
   「正确但没用」，但自动回复**确实给出了 TPU 软胶这一正确参数**，只是结尾又加了
   「可以查看详情页」。claim 级判官会记为「准确且针对性强」，与人工的整体判断
   产生 2 档分歧。*改进*：对这类「答了但仍让用户多走一步」的回复单列
   **「尾部推诿」**信号，而不是靠一个整体分把它掩盖掉。

**还有一类系统性的盲区需要单独说**：本方法评的是**回复文本**，
评不了「用户是否真的满意」。它不能替代线上 A/B 与满意度（CSAT）监测。
**建议的用法**：本流水线作为**发布前的回归闸门 + 问题的定位器**
（指出「哪些意图、哪类话术在拖后腿」），
线上真实效果仍由 A/B 与 CSAT 决定。

## 六、AI 工具使用情况

| 环节 | 用了什么 | 人做了什么 |
| --- | --- | --- |
| 需求拆解 | 用 AI 把「准确/有用/语气好/不能瞎编」列了几种拆法 | 决定拆成 5 个指标、决定「有用」必须拆成解决力 + 完备性（因为修复手段不同） |
| 数据理解 | 让 AI 汇总 20 条人工批注，找重复出现的批评点 | 判断出「主动服务 / 能力边界」才是批注的真正主线 |
| 代码生成 | AI 生成了 `src/` 与 `run_eval.py` 的骨架、正则、SVG 图表 | 逐条复核正则的对错；发现并修掉 3 个问题（见下） |
| 指标校准 | — | 全部人工：权重、闸门阈值、等级区间、rubric 锚点都是手调的，且写死进代码供复核 |
| 方法自检 | AI 生成对抗样本的初稿 | 人工确认「预期结果」，并据此发现真漏洞 |

**AI 生成后由人工发现并修掉的问题**（这部分值得单列，因为它说明 AI 输出必须被验证）：

1. **先验平滑把编造洗白了**：一句「退款最慢不超过 3 小时」在原来的公式里只能拿到
   0.73 的无编造分，闸门不触发。→ 补了一条硬规定：整条回复没有被支持的断言、
   只有高风险无依据断言时直接封顶 0.50。
2. **空口承诺没纳入事实校验**：「我们会赔偿您 1000 元」被归为「承诺」，直接跳过校验。
   → 新增 `commitment_amount` 断言类型。
3. **推诿正则漏召回**：「请在订单详情页查看」只匹配了「**商品**详情页」，
   「我可以在物流追踪页面查看」也没命中，导致 `case_17` 被误判成 89.9 分（最高分）。
   → 扩写模式，并新增「首句即推诿则封顶 3.0」。
4. **修 3 之后引入的假阳性**：金额承诺的正则把「优惠券 1.未达到门槛 2.已过期」
   这种排号列表当成了金额。→ 收窄触发词，并把这个 case 加进对抗集。

> 这四个问题只看总分都不会被发现——它们分别是「分数偏高但不合理」
> 「分数正常但逻辑错」「分数偏高且排序错」「分数偏低但没法解释」。
> 所以 `validate.py` 里的断言校验是必需品，不是可选项。

## 八、如何看结果（截图指引）

1. **运行结果**：
   ```bash
   python3 run_eval.py      # 终端会打印逐条得分表 + 整体统计（见本文档第四节）
   python3 validate.py      # 终端会打印对抗集压测结果 + 断言通过数
   ```
   两个脚本的终端输出都可直接作为「运行结果截图」。

2. **可视化看板**：直接双击打开 `outputs/dashboard.html`
   （纯静态单文件，不依赖服务器），页面上依次是：
   ① 总分分布 ② 各指标得分率 ③ 人工档位 × 自动总分散点 ④ 最差 3 条 case ⑤ 逐条明细表。

3. **逐条复核**：`outputs/scores.csv`（得分）与 `outputs/claims.csv`（断言级依据）。
